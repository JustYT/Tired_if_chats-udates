# Инструкция для Codex: код релиза Саммаризатора чатов

Это чистый репозиторий обновлений. Для первой установки обычно используется
отдельный исходный архив, содержащий ключ только для чтения. Не подключай
учётные данные другого человека, не копируй старые SQLite, профили Codex и
токены. В репозитории их нет. Подробности команд — в `README.md` рядом.

## 1. Определи ВМ и владельца

Нужны три значения: SSH-хост ВМ, Linux-логин для SSH (`VM_LOGIN`) и staff-логин
будущего владельца Саммаризатора (`STAFF_LOGIN`). Бери их из сообщения пользователя
или проверенного контекста текущей задачи. Не угадывай по имени отправителя
архива. Если Codex уже работает прямо на целевой ВМ, SSH-хост не нужен.
Если адрес дан как `ssh://HOST`, для команд используй `HOST` без схемы.
При отсутствии этих данных спроси их до установки.

Убедись, что на ВМ Linux, Python 3.10+, пользовательский systemd и SSH. Для
Codex-подписки нужны `/usr/bin/bwrap`, `/usr/bin/prlimit` и установленный
администратором, защищённый от записи обычным пользователем Codex CLI.
На аналогичной Ubuntu-ВМ при отсутствии `bwrap` можно установить пакет
`bubblewrap`. Если нет прав на установку, явно сообщи, что функция Codex
недоступна; Мессенджер, Wiki и модель Стефании могут работать отдельно.

## 2. Установи без перезаписи чужих данных

Проверь, свободны ли `~/.config/systemd/user/chat-studio.service`,
`~/.local/opt/chat-studio` и `~/.local/share/chat-studio/studio.sqlite3`.
Если уже заняты, не удаляй и не перезаписывай их: сначала выясни, чей это
экземпляр и нужно ли обновление или отдельная установка.

Клонируй закреплённый релиз прямо на целевую ВМ и запусти:

```sh
git clone --branch v2.2.0 --depth 1 https://github.com/JustYT/Tired_if_chats-udates.git chat-summarizer-source
cd chat-summarizer-source
./install.sh STAFF_LOGIN
```

Прямое клонирование требует собственный GitHub-доступ владельца ВМ. Если
пользователь передал исходный архив, используй его вместо этого клона:
в нём уже есть ключ чтения и отдельная инструкция DEPLOY_AGENT.md.

Если `8765` занят, передай свободный порт вторым аргументом, например `8876`.
Установщик создаёт новую SQLite и пользовательскую службу. Проверь статус
`systemctl --user status chat-studio.service` и
`curl -fsS http://127.0.0.1:PORT/api/health`.
Проверь `/api/bootstrap` программно, выводя только логин, количество чатов,
выбранных чатов и заданий: при новой установке все три количества равны нулю,
оба расписания выключены. Не печатай полный ответ с CSRF-токеном.

Проверь, переживёт ли пользовательский systemd выход из SSH:
`loginctl show-user VM_LOGIN -p Linger --value`. При выключенном linger и
наличии соответствующих прав включи его; иначе сообщи об ограничении.

## 3. Подключи только собственные токены получателя

Команду подключения запускай на машине, где работает Codex получателя и в
окружении **его** Стефании доступен `MESSENGER_TOKEN`. Для Wiki дополнительно
нужен его `WIKI_TOKEN`; для корпоративной модели — его
`ANTHROPIC_AUTH_TOKEN`; для отправки ботом — его `CHAT_STUDIO_BOT_TOKEN` и
`CHAT_STUDIO_BOT_LOGIN`. Эти переменные необязательны, кроме токена
Мессенджера. Если нужных токенов нет, не ищи чужие файлы и не проси вставить
значения в чат; оставь соответствующее подключение выключенным и объясни,
какую переменную должен подготовить владелец.

Из этого клона на машине получателя запусти:

```sh
python3 connect-remote.py --host VM_HOST --ssh-user VM_LOGIN --owner STAFF_LOGIN
```

Первый обычный SSH-вход нужен для проверки host key. Подключатель передаёт
значения через SSH stdin, сверяет `STAFF_LOGIN` с владельцем службы и импортирует
их в оперативное окружение пользовательского systemd. Не выводи значения env,
не записывай их в `.env`, unit-файл, командную строку, логи или итоговый ответ.
После перезагрузки ВМ импорт нужно повторить. Если Codex запущен на самой ВМ
и токены есть в его shell, можно выполнить `./connect-env.sh` там.

Личная подписка Codex подключается отдельно кнопкой входа в UI владельцем;
не копируй его `auth.json` с другого устройства.

## 4. Дай владельцу доступ и отчитайся

Сервер намеренно слушает только `127.0.0.1`. Открой с компьютера владельца
SSH-туннель с **одинаковым локальным и удалённым портом**:

```sh
ssh -N -L 127.0.0.1:PORT:127.0.0.1:PORT VM_LOGIN@VM_HOST
```

Адрес интерфейса — `http://127.0.0.1:PORT/`. Не публикуй HTTP на внешнем
интерфейсе: отдельной веб-аутентификации нет. Проверь, что UI отдаёт страницу,
а подключённые сервисы показывают ожидаемый статус. Не включай расписания и
не запускай отправку саммари без отдельного выбора владельца: тестовый запуск
отправляет результат сразу.

В отчёте укажи адрес через туннель, владельца установки, статус службы,
какие подключения реально проверены и что осталось настроить. Не называй
подключение готовым, если только импортированы переменные без проверки доступа.
